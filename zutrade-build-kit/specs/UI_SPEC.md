# 界面实现与验收

视觉参考为 references/approved-ui.png，旧交互参考为 references/workbench-prototype.html。图片已获用户认可；原型只有演示逻辑，不代表已经实现服务端、AI 或渠道。请用工程中的 React 组件实现对应交互，不能把旧 HTML 直接作为整个应用嵌入，也不要复制其中为演示方便而使用的外部 CDN 依赖或本地临时状态来替代业务接口。

## 信息结构

| 入口 | 首屏重点 | 主要动作 |
| --- | --- | --- |
| 消息 | 会话列表与当前买家聊天 | 阅读、认领、接管、受控回复、内部备注、报价/审批 |
| 找客户 | 真实研究条件与候选列表 | 目录/关键词发现、核对证据、去重、确认线索、建立批次 |
| 产品 | 工厂与产品、可用资料、待确认项 | 来源上传、事实确认、价阶与有效期维护 |
| 待办 | 需要人处理的事情 | owner 审批、资料补齐、跟进到期、失败/未知结果核对 |

不要把复杂数据库结构直接铺成菜单。客户卡、商机、资料与报价历史按需展开；重要操作可从聊天内部工作区进入。

## 视觉与交互

- 白色、浅灰为底，绿色作为有限主操作强调色；克制的分隔线、留白和字体层级。
- 窄导航、适中会话列表、宽聊天区；桌面默认不同时展开多个大抽屉。
- 买家消息与“仅团队可见”的 AI/报价/备注区域明确分开。使用边界和标题表达身份，不只依赖颜色。
- 真实研究结果、模拟消息、模拟 AI 各自显示准确标识；状态来自服务端，不用本地 toast 假装持久化完成。
- 中英文长内容可换行；金额和版本清楚；请求中禁用重复提交并提供恢复方式；失败要能看到原因并按正确协议重试。
- 键盘可聚焦、按钮有文字或可访问名称、明显焦点状态。审批确认必须能看到实际正文、收件人与附件版本。
- 手机为列表到单会话的导航，详情和内部区按需打开；支持紧急查看、接管和审批。批次复杂编辑可引导回桌面。

## 必须检查的界面状态

有数据、空列表、加载、分页、权限拒绝、版本冲突、网络断开、后台任务处理中、模拟完成、失败、unknown 待核对、审批过期、资料缺失。

在约 1440 像素桌面与约 390 像素手机宽度检查布局。不得只凭编译成功声称界面通过，也不要求每个像素与生成图片完全一致；以信息层级、操作流与可读性为验收依据。

## 小团队协作

已读位置按成员独立保存，负责人表示推进责任，不能代替访问权限。接管必须得到服务端确认；另一成员看到最新状态。两人修改同一业务对象时使用 expected_version，冲突有清楚提示，不静默覆盖。

未分配工厂的会话只进入 owner 分配队列。混合多个工厂的会话，读取完整消息、搜索摘要、备注、SSE 和附件需要对全部关联工厂有权限；不能只因其中一个商机可见就显示整段历史。
