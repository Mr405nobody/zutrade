# ZuTrade Codex 分阶段建设提示词

本任务书用于让 Codex 从零建设 ZuTrade 的本地完整首版，按 9 个阶段逐项交付并等待用户验收。运行条件为 Mac 与 Docker；消息收发和 AI 使用可重复模拟，海外公司发现必须真实联网并保存来源。技术架构沿用 React、NestJS、独立 worker、PostgreSQL、Drizzle、Better Auth 与 pg-boss。

完整交接包包括所有独立阶段提示词、合并版、数据库实施说明、原始 42 表 SQL、架构与产品资料、已认可的 UI 图片、旧交互参考及进度模板。Codex 应直接读取这些本地输入，不依赖 ChatGPT 私有页面。本任务书规定 D1 使用增量迁移新增研究任务表；本次交付未执行该迁移或创建应用。

# 1 使用方法

本包用于让 Codex 从零建设 ZuTrade 本地完整首版。你每次只启动一个阶段，验收后再启动下一阶段。任务范围确认于 2026 年 10 月 28 日。

## 你已经确定的范围

- Mac 开发环境，可以使用 Docker；本轮不部署线上环境。
- 你与 1—4 名成员替工厂销售；工厂作为签约、收款和履约主体。
- 微信式桌面工作台，四个入口：消息、找客户、产品、待办。手机支持紧急查看、接管和审批。
- 买家收发使用 MockAdapter，AI 使用可重复的 MockAIProvider。
- 找客户必须真实读取公开网站或搜索 API，并保存来源。模拟 AI 不承担任意网页的通用语义理解。
- 业务闭环做到可信报价、owner 审批、模拟外发与明确跟进。本轮不接正式消息渠道、真实大模型、订单、收款、物流和佣金结算。

## 怎样开始

1. 在 Mac 上新建一个项目目录，例如 ZuTrade。
2. 将本压缩包解压后得到的 zutrade-build-kit 文件夹放进这个项目目录。
3. 在 Codex 中打开项目目录 ZuTrade。后续 apps、packages、infra 等工程目录建在 ZuTrade 根目录，交接资料保留在 zutrade-build-kit 中。
4. 将下面这段开工提示词发给 Codex。

```text
请以当前打开目录作为 ZuTrade 项目根目录。
先阅读 zutrade-build-kit/MASTER_PROMPT.md、zutrade-build-kit/specs/CONFIRMED_SCOPE.md、zutrade-build-kit/specs/DATABASE_NOTES.md，以及 zutrade-build-kit/stages/00-bootstrap.md。
按照其中的约束执行阶段 0。需要查阅的其他文件都在 zutrade-build-kit 中，请直接读取，不要假设你能打开我在 ChatGPT 中的私有页面。
本次只授权完成阶段 0。请真正建立并运行工程骨架，完成本阶段验证、交付启动方式和人工验收步骤，再停在 ready_for_user_review 等待我验收。
本轮不执行 A1 或后续阶段，不接真实 AI、不发送真实消息、不部署线上环境。
```

如果 Codex 打开的目录中已经有代码，先让它检查现有状态和根目录位置，再继续；不需要为了使用本包删除原目录。

## 每次启动下一阶段

前一阶段验收通过后，发送：

```text
我已验收通过阶段 0。现在只执行阶段 A1。
请重新读取 zutrade-build-kit/MASTER_PROMPT.md、zutrade-build-kit/stages/A1-identity-database.md，以及仓库 docs/build 下的 PROGRESS、HANDOFF 和上一阶段验收报告。
先核对现有代码、迁移记录和 Git 状态，再继续建设。完成 A1 后给出实际验证结果和人工验收步骤，停在 ready_for_user_review，不进入 A2。
```

之后将阶段 ID 和阶段文件名替换为对应项。换会话时使用 prompts/RESUME.md；验收发现问题时使用 prompts/FIX_CURRENT_STAGE.md。

## 真实网络能力如何验收

找客户有两条真实路径：公开企业目录发现，以及配置搜索 API 后的关键词发现。必须至少完成一条真实联网发现闭环。若没有搜索 API 凭据，公开目录模式仍需真实从目录链接发现企业，不能只读取事先手写的公司名单来冒充发现。

关键词搜索 API 若尚未配置，界面及验收报告标明不可用，不自动替换为演示结果。两条真实来源都被环境阻塞时，D1 停在 verification_blocked，等待所需网络或来源条件；不能用离线测试通过代替真实联网验收。

本包是建设提示词和输入资料，尚未创建实际应用。原始 SQL 的既有约束验证不等于新工程的集成、并发或浏览器验收已经完成。

你是负责交付 ZuTrade 的资深全栈工程师。请在当前工作目录中建设真正可运行的本地应用，并以用户本次明确指定的阶段为执行边界。遵守当前环境的系统指令、权限规则和仓库已有指令；下文是本项目的用户需求与交付约定。

ZuTrade 是供 owner 与 1—4 名销售成员使用的代理销售工作台。团队替工厂寻找海外买家、处理消息、确认需求、生成可信报价并安排跟进。日常工作从消息开始。工厂仍是签约、收款和履约主体。

这次从零建立正式工程，运行在 Mac 与 Docker 上。完成前端、API、PostgreSQL、worker、认证、权限、报价、审批和跟进的真实实现。消息收发和 AI 使用明确标识的模拟适配器；海外企业发现必须真实联网。当前阶段的代码、验证和文档都完成后，停止等待用户验收。

## 3 技术基线

| 层 | 采用方案 |
| --- | --- |
| 工程 | TypeScript、pnpm workspace、单仓库；Node 24 的兼容稳定补丁版本；提交锁文件 |
| 前端 | React、Vite、Tailwind、shadcn/ui、Lucide、TanStack Query |
| 服务端 | NestJS；API 与独立 worker 共享领域模块；配置兼容 pg-boss 的 ESM 运行方式 |
| 数据 | PostgreSQL 18、Drizzle ORM、node-postgres；SQL 迁移保留原生约束、触发器和 RLS |
| 任务 | pg-boss；业务变更、outbox 事件身份和入队使用同一数据库事务 |
| 认证 | Better Auth；官方生成认证 schema；业务成员角色由 ZuTrade 管理 |
| AI | MockAIProvider + Zod 契约；保留 AI SDK 的未来接入边界，本轮不调用真实模型 |
| 通信 | REST 命令/查询、OpenAPI 类型、SSE 变化通知；重连后回到数据库补查 |
| 文件 | 私有文件存储接口；本地使用受鉴权的磁盘适配器，未来可替换 S3 兼容适配器 |
| 测试 | Vitest、真实 PostgreSQL 集成测试、Playwright 关键浏览器路径；具体兼容版本在阶段 0 锁定 |

先核对所选锁定版本的官方文档和依赖要求，建立可构建的版本组合。不要凭记忆编造当前 API，也不要为追新无故更换已选组件。pg-boss 的既有研究基线是 12.38.0；确有兼容或安全问题时记录 ADR 并选择合适补丁，不能退回两套任务调度器。

代码根结构至少包括 apps/web、apps/api、apps/worker、packages/domain、packages/db、packages/contracts、packages/channels、packages/ai、packages/ui、infra。真实获客的网络实现可以放 packages/prospecting；业务研究与销售线索归属由 domain 的 Prospecting 模块管理。

不引入 Kafka、Kubernetes、Redis、独立向量数据库、多服务 RPC、完整 CRM 框架或可视化工作流平台，除非当前用户另行变更范围。不要将 Chatwoot、Twenty 等完整系统接成第二个客户、会话或审批主库。

## 4 三种运行模式分别控制

必须独立表达以下三个语义，不使用一个 DEMO_MODE 把它们混在一起：

```text
消息渠道：simulation
AI 执行：preset / mock
企业发现：live_public_directory 或 live_search_api
```

工程不注册真实邮件、WhatsApp 或其他消息发送适配器，不加载真实模型凭据。真实获客只允许读取公开来源或搜索接口，不能因此启用真实触达。所有消息模拟记录持续标识为模拟，数据库不能写成真实已送达。

MockAIProvider 的相同规范化输入、场景版本和时钟产生相同结果。无法覆盖的输入转为待人工处理，不伪装成通用模型理解。真实检索失败时返回清楚的错误和重试入口，不悄悄使用 fixture。

## 5 不可省略的领域规则

1. workspace 是 ZuTrade 的运营组织，factory 是被代理的工厂。两者不可混为租户。首版工厂不登录。
2. buyer、contact、contact_point、thread、opportunity、quote version 和 followup 分开建模；一段会话可以关联多个商机。A2 即建立最小 intake 商机来确定工厂归属；未归属会话只对 owner 开放。完整 thread 只有在关联工厂全部可见时才能读取，不能由单个可见商机放行混合历史。
3. owner 与 sales 是实际启用角色。报价、折扣、交期等商业承诺只有当前有效且被工作区指定的 owner 可以批准。
4. 供给事实需要工厂、来源版本、确认人、有效期和对外可用范围；网上找到的买家研究资料不能直接成为报价或交期依据。
5. 金额由确定性计算器计算。数据库使用 numeric，传输使用十进制字符串，计算使用可靠十进制实现。未知费用保持未知，不能变成零。
6. 报价正文、卖方、收件人、账号、条款、附件字节及摘要在审批前确定。审批绑定具体冻结版本和规范化摘要。实质内容修改后重建版本、重新审批。
7. 普通回复、FAQ、报价、批次、跟进都经过同一个发送网关。浏览器和 AI 不直接调用适配器 send，调用端不能自行选择免审授权模式。
8. 网关在一个短事务中检查当前权限、证据、报价、联系资格、入站屏障、会话版本、审批与发送幂等状态，并原子领取发送权；网络请求在事务提交后执行。
9. claimed 的事务提交是撤销截止点。pg-boss 领取任务不是领取发送权；claimed 之后不能承诺此次发送已撤回。
10. 外部结果不确定时进入 unknown 并核对。没有服务方幂等能力时不能盲目自动重发；重复任务不能生成新的业务发送身份。
11. 买家新回复、人工接管、退订、报价失效、需求变化和跟进改期会阻挡旧动作。取消队列任务只是优化，业务版本检查才是执行依据。human 模式停止自动 FAQ、自动跟进和接管前的旧计划，但允许当前有权成员新发起、满足最新版本和审批条件的人工回复/报价/明确批次动作；paused 模式另行停止新外发。不能把人工接管理解为人工也不能回复。
12. 原始入站收据与发送领取共享渠道账号锁；尚未处理的收据形成入站屏障，不能因任务失败而直接解除。
13. 内部团队笔记、AI 建议、成本和其他工厂资料不属于买家消息，不能混入外发快照。
14. API 与 worker 的业务连接使用非表 owner、非 superuser、无 BYPASSRLS 的角色。成员资格验证后在事务内设置租户上下文，防止连接池串租户。
15. 业务变更、outbox 事件记录与 pg-boss enqueue 在同一事务。outbox 不再承担第二套发布、重试或租约机制。

## 6 模拟 AI 阶段的自由文本发送规则

本轮没有可靠的通用语义判定模型。免审自动回复和 sales 普通回复仅使用经过审核的常规事实/澄清模板及受控字段。未知自由文本保持内部草稿，进入 owner 审核；不能靠几个价格关键词就声称已证明其没有商业承诺。

owner 确认自由文本时，也应冻结最终外发内容并记录审批。用户的开发阶段验收，与系统中的业务 owner 审批，是两个独立流程；前者不能替代后者。

## 7 数据库与迁移

references/zutrade-schema-v1.sql 必须保持原始字节不变，其 SHA256 为 b7f72b68adce6ad161eedf66b65389cd35461ec20446a9e97fa560550c21a1fe。阶段 A1 安装这 42 张业务表；Better Auth 与 pg-boss 的表由各自官方迁移管理。

阶段 D1 为真实研究任务增加最小的 prospecting_runs 及 leads 关联字段，预期变为 43 张业务表。通过增量迁移实现，不能静默改写已执行的基线，也不能把表数量当成永久不变的测试断言。

Drizzle 映射不完整表达的约束必须保留在 SQL 迁移中。禁止用自动 schema push 删除冻结保护、复合外键或 RLS 来消除差异。迁移事务边界、身份映射和初始 workspace 创建遵循 DATABASE_NOTES。

测试使用独立数据库或隔离 namespace，不清空用户日常演示数据。重置命令显式命名为破坏性操作，只用于明确指定的 disposable 数据；日常启动、迁移、seed 不能暗中 reset。

## 8 界面与体验

采用用户已认可的微信式布局。主界面中文，买家内容可为英文；浏览器本地时区显示，工作区默认 Asia/Shanghai，数据库保存 UTC 时间与必要 IANA 时区。

左侧为简洁四入口导航，消息页是会话列表与宽聊天区。客户资料、商机和证据按需展开，内部 AI/报价区与买家对话明确区分。不要先做密集仪表盘、常驻四大侧栏或为 43 张表生成 43 个管理页面。

按钮要有真实后端行为、加载/失败/空状态和权限反馈；阶段尚未实现的动作隐藏或说明，不放假成功 toast。手机保留查看、接管、普通模板回复与紧急审批；复杂批次编辑以桌面为主。

## 12 最终目标

## A1 42 表基线 Drizzle 与事务包装

- 参考文件：`zutrade-schema-v1.sql`，75,172 字节，SHA256 `b7f72b68adce6ad161eedf66b65389cd35461ec20446a9e97fa560550c21a1fe`。原件只读保存；校验不符时先定位差异，不悄悄更新期望值。
- 基线有外层 `BEGIN;`（第 64 行）与末尾 `COMMIT;`。先核实锁定版本 Drizzle runner 的实际事务行为。若 runner 已包事务，生成迁移副本时仅移除这两个已确认的顶层包装，保留函数、DO 块、触发器及所有 SQL 内容；禁止全局替换 BEGIN/COMMIT。保留可复现的转换和差异校验，不能把内层 COMMIT 交给外层 runner 后假定仍然原子。
- 迁移与迁移日志应由同一明确的事务边界管理。新数据库执行一次；重复执行迁移命令不得重建已有表。已有库通过后续增量迁移演进。
- Drizzle 映射以 SQL 的真实列名、精度、可空性、复合键为准；不能用 ORM 自动推送覆盖自定义约束、RLS 和触发器。认证与 pg-boss 的表由其锁定版本官方流程管理，另计数量。
- 验收：Docker PostgreSQL 18 全量建库；业务表恰为 42 张；对比重要约束/策略/触发器；中途失败不留下半套业务表或错误成功日志；再次运行迁移无破坏。既有 PGlite 结果不能代替这一步。

## A1 auth_subject 映射与未选 workspace 的 RLS 循环

现有策略依赖 `app.user_id` 或 `app.workspace_id`，不能直接假定登录后即可查询映射、列出成员资格。采用正常 runtime 角色加窄范围 SELECT 策略解决，不开全局 BYPASSRLS。

1. 服务端先通过 Better Auth 的真实会话验证取得可信 `auth_subject`；不能使用客户端自行声称的 subject/user/role。
2. 在身份解析事务内设置事务局部的已验证 subject 上下文。以增量迁移增加仅匹配该 subject 的 `app_users` 自身读取策略；必要时收紧映射写入策略。先得到规范 `app_user.id`，再设置事务局部 `app.user_id`。普通资料接口不能修改 auth_subject。
3. 首次登录可创建不带业务权限的用户映射；并发首次登录依据唯一 auth_subject 收敛到同一 user ID。禁止把“第一个登录的人”自动升为 owner。
4. 增加 `workspace_members` 的 SELECT-only 自身成员资格策略，使 workspace 尚未选择时也能读取本人活跃成员记录；需要显示工作区名称时，给 workspaces 增加通过本人活跃成员资格的 SELECT-only 策略。策略依赖应单向，不能形成相互递归。
5. 客户端提交 workspace ID 只是选择意图。服务端确认本人活跃成员资格后才建立业务事务的 workspace 上下文。无成员返回空列表；禁止先设置任意 workspace 再利用宽范围读取反推权限。
6. 新增身份发现策略不能是 FOR ALL，也不能扩大成员增删改权限。开发 owner/sales 由显式本地 seed 建立；审批仍只允许活跃且被指定的 owner。

验收：没有 workspace 上下文也能完成自己的身份解析和成员发现；无成员账号看不到业务；外来 workspace ID 被拒绝；过期会话不触发身份引导；并发首次登录不生成两份映射；连接池在提交、回滚及跨用户交替请求后不残留上下文。

## A1 A2 C 运行身份 pg-boss 与发送协议

- 迁移/初始化角色与 API、worker runtime 分离。后者不拥有业务表、不是 superuser、没有 BYPASSRLS；`app`、`auth`、队列 schema 各授必要权限。pg-boss 初始化/升级走受控迁移身份，不为方便启动给 worker 永久 DDL 或 owner 权限；配置方式核对安装版本官方接口。
- API、worker 均在真实业务事务内使用参数化的事务局部上下文设置。后台任务的 workspace/member 参数只用于定位；重新读取事件和目标对象、校验归属、当前成员权限与工厂访问范围。不能把 worker 当作万能 owner。成员发起任务重新核验该成员；已授权入站处理/FAQ 等系统任务按可信账号与当前策略限定范围，记录系统 actor，不能伪造 owner 身份，也不要求买家 webhook 拥有成员会话。
- 业务变化、outbox 事件身份与 pg-boss enqueue 必须使用同一个 PostgreSQL 事务连接；不能在 Drizzle 事务中另从池取得一个 pg-boss 连接。outbox 不再建设独立发布、lease 或 retry 调度器。
- 验收：注入 enqueue 前后异常，业务、事件、任务共同回滚；重复命令不重复创建外发；两个工作区任务并发执行互不串租户；重启 worker 不丢失已提交任务。
- C 阶段统一网关检查最终冻结内容、审批、事实、需求、联系资格和接管状态。webhook 收据与 claim 共用账号锁；未标准化入站屏障阻止旧自动发送。提交 claimed 是撤销截止，领取 pg-boss job 不是领取发送权。
- 并发撤销、双 worker、回执乱序、接收成功但响应丢失都要验收。unknown 不盲目重发；失去领取权的旧 worker 不得继续发送。A2 若先实现普通模拟回复，也必须经过同一网关入口，商业承诺先拒绝或留待 C。

C 阶段的 Mock 接收账本使用隔离的 simulation schema 与独立连接，接收提交不参与 app 业务投影事务，以复现远端已接受而本地未写回的情况。它由本地模拟设施管理，不计入 app 的 42/43 张业务表；普通 API 业务角色无修改权限。幂等/非幂等能力按场景准确实现，跨 worker 和重启保留记录。过期 claimed 没有服务方幂等保证时进入核对，不因队列 lease 到期自动生成第二次发送权。

### 任务表要求

- 正式列保存 workspace、factory、发起成员、provider/发现模式、状态、幂等键、请求摘要、结果版本、计数、任务关联、开始/结束时间及错误。用复合 FK 约束租户、工厂和成员归属；搜索前明确代表哪家工厂。
- 正式区分搜索 API 与公开目录发现。请求配置与结果快照使用有结构校验的 JSON；每批候选上限、单项摘录长度、总快照体积、抓取页数和超时都设硬上限。默认 20 条、硬上限 50 条，单项摘录及 512 KiB 总快照体积限制见 PROSPECTING_SPEC。
- 候选 key 在本次 run 内稳定；结果版本用于拒绝过期导入。终态快照保留，重新搜索生成新 run，不覆盖已导入线索当时的证据。
- results_snapshot 在终态冻结；review_decisions 独立保存每个 candidate 的保留/排除、理由、操作者和时间，配独立 review_revision/CAS 与追加审计。更新审核决定不能改变来源证据；导入必须检查当前审核版本及决定。
- first_started_at、固定 deadline、累计请求计数和检查点持久化到 run。跳转、重试及 HEAD/GET 均计预算；每次请求前原子占用预算，多个 worker 和重启共享同一上限。终态/到期后不继续写结果。
- 每项保留来源 URL、最终 URL、获取时间、标题、摘录/允许保存的证据、摘要哈希及读取状态。搜索摘要、官网已读取、人工确认要区分；不能从搜索词推断公司所在地或采购意愿。
- Brave 等 provider 按实际套餐/条款确认允许持久化的内容；没有存储许可时不能默认保留全部返回数据。目录 URL 模式仍须真实读取和校验。凭据/网络失败显示失败或部分完成，不用种子公司替代成功结果。
- 新表显式增加 RLS、运行角色授权、必要索引和审计；基线中的建表后循环不会自动保护未来新增表。

### 线索导入要求

- leads 两个新字段必须同时为空或同时非空；以 `(workspace_id, factory_id, prospecting_run_id)` 复合关联任务，并对 workspace/run/candidate key 建唯一约束。
- 导入服务只接受 run ID、candidate key、预期结果版本及必要人工选择，从数据库读取真实快照；不相信客户端重传的公司名和证据 JSON。
- 导入时同时核查最新审核决定及版本；被排除或证据版本不匹配的候选拒绝导入，返回冲突/状态原因。
- 现有 leads 的 buyer_id/factory_id 非空：原始候选先存在 run；确认身份后创建或关联 buyer，再建 lead。模糊名称/相似域名只能给合并建议，不能自动认定同一实体。
- 买家/联系人/线索创建与来源复制同事务。并发重复导入同一候选必须返回同一 lead，不能留下多余 buyer/contact。公开联系方式不自动写为允许联系；真实公司上的模拟沟通仍明显标注模拟。

# 5 真实获客实施要求

| PublicDirectoryProvider | 从公开企业/协会/行业目录的列表页发现企业链接，再读取可访问的企业信息页或官网 | 至少一个实际可访问且允许当前读取方式的公开目录，真实网络可用 |
| BraveSearchProvider | 调用正式 Web Search API 获取候选，按限制读取来源页面并建立证据 | 本地 API 凭据、有效账号与允许保存所需搜索结果的权利 |
| FixtureResearchProvider | 离线自动化测试，复现异常与解析边界 | 仅测试环境使用；不能作为真实获客运行时的静默 fallback |

PublicDirectoryProvider 不是手写公司名单。目录 URL 和必要的列表提取配置可以是显式配置；企业候选必须从本次真实响应中发现。不要将 Google、LinkedIn 或其他服务的登录页面、验证码、被拒绝的网页抓取视为可绕过的阻碍。

D1 交付时至少提供一个由 Codex 在执行当时实际验证的公开目录配置，并说明它覆盖的行业与地区；不能只有空的 URL 输入框和一个未实现的通用爬虫接口。来源确实不可用时报告具体阻塞并请求所需来源条件，不编造可用 URL。

关键词搜索不可用时，界面显示配置状态，并提供已可用的公开目录模式。未配置 API 的路径不能显示已通过真实联网验收。任何提供方都没有真实可用来源时，D1 进入 verification_blocked。

## 2 输入与首版合理默认

- 默认目标案例：CT-01 棉布袋，海外活动组织公司、礼品代理/促销品分销商；可选择新加坡、澳大利亚或英国。国家输入是搜索意图，不是企业所在地证明。
- 公司关键词优先使用公开业务词，不把买家聊天正文、个人资料、工厂成本或内部合同发送给搜索服务。
- 默认每次研究最多 20 家候选，允许配置但硬上限 50。所有请求需要总预算而不是只限制单页数量。
- 默认每个企业最多读取 3 页（例如主页、关于、联系），目录最多 5 页，总 HTTP 请求上限 80。仅执行 GET/HEAD，不提交表单或触发外部写操作。
- 默认并发 2；每个主机最多 1 个并发请求，并按其允许节奏访问。单次请求 10 秒、重定向最多 3 跳、单响应解压后不超过 2 MiB、总研究 180 秒；重试至多 2 次且受总预算约束。
- API provider 的参数与上限以执行时官方文档为准。本地默认比上游上限更保守；429 尊重 Retry-After，并显示额度/速率问题，不能切账号绕过限制。

这些值是本项目工程默认，不是第三方服务能力或性能保证。用户可以在明确配置中调整，仍保持硬限制。

预算按整个 prospecting_run 持久化：首次开始时间、固定 deadline、累计请求次数与检查点在数据库中保存。每次 HTTP 请求前原子占用额度，重定向、重试及 HEAD/GET 都计入同一上限。worker 重试/重启不获得新预算，超时后结束为 partial/failed 等明确终态并冻结结果；用户重新研究创建新 run，不能覆盖旧证据。

## 3 候选与证据契约

每个 candidate 有稳定候选键、来源模式、公司名称/候选名称、规范化域名、可证实国家、业务描述、公开联系方式、匹配理由、规则版本、已知记录关联、未知字段和排除理由。

每条 evidence 至少包括：

- 来源 URL、跳转后的最终 URL、来源类型（搜索摘要/目录/官网/人工确认）。
- 实际获取时间 observed_at、读取状态、页面标题、必要短摘录或结构化字段、内容摘要 hash。
- 证据支持的字段路径，提取器版本、发现链（从哪张目录或搜索结果到达）。
- 获取失败的明确原因；未获取到正文时不生成正文 hash，不显示已读官网。

单个摘录默认不超过 500 个字符，每项最多 3 条必要摘录，结果 JSON 总上限 512 KiB；超限时截断候选数量并记录原因，不静默丢掉已被导入线索依赖的来源。内容摘要是完整已获取正文或明确规范化文本的 hash，两者的 hash_scope 必须记录，避免让摘录 hash 冒充整页证据。

保存必要来源与事实依据，不把整站复制到数据库。来源许可不允许留存的数据不应保留；不能通过变换字段或 hash 规避留存约束。搜索 API 未取得所需留存权时保持未启用或改用可用公开目录模式，不能仅加免责声明后继续存储。

## 4 提取 匹配与去重

HTML 以文本/DOM 数据解析，可用 Cheerio，不执行页面脚本。优先读取明确的企业名称、联系方式及公开结构化数据；抽取结果保持来源定位。SPA、登录页、验证码或拒绝访问返回 unsupported/blocked 状态，不伪造成功。

匹配使用明确规则和版本，例如已证实地区、活动/促销品业务关键词、产品用途和排除词。每一条加减分都对应证据。没有支持则输出 unknown；不得从“官网在新加坡搜索结果中出现”推断公司一定在新加坡，更不能据此断言有采购预算。

域名去重采用明确规范化，保留原始来源 URL；只移除已知跟踪参数，不能任意删除具有页面语义的 query。注册域名可提示重复，但分支机构、共享平台子域名和不同法律实体必须允许人工区分。

同一公司不同研究任务产生不同观察历史。终态快照不覆盖；再次研究创建新 run，已导入线索继续引用当时观察。确认候选时从服务端快照取值，不能信任浏览器回传的研究正文。

保留/排除候选的操作写入 prospecting_runs.review_decisions，由 candidate key 定位，包含理由、操作者、时间和独立审核版本；每次更新使用 CAS 并写审计。不可变 results_snapshot 不承担审核状态。导入时同时检查证据版本与当前审核决定，已排除候选不可通过旧浏览器状态导入。

## 5 抓取边界

只允许 HTTP(S) 公共网页与固定的正式搜索 API endpoint；禁止任意协议、URL 凭据、异常端口、回环/私网/保留/链路本地/云元数据及 Docker 内网目标。IPv4、IPv6、映射地址和异常表示都要规范化验证。

对每次实际请求和每次跳转校验完整 DNS A/AAAA 结果与目标，拒绝不允许的地址。实际连接使用已验证地址，同时保持正确 Host/SNI、证书验证；避免校验后另一次 DNS 解析带来绕过。不能仅用正则检查 URL 或仅验证第一跳。若所选 HTTP 库无法安全完成这条链，改用能证明边界的 transport 实现，而不是放宽限制。

外部网页的请求不携带搜索服务 API key、用户 cookie、内部 Authorization 或来源页敏感头。响应内容不执行脚本、命令或模型指令；客户端展示进行清洗或纯文本渲染，链接使用安全打开方式。

离线测试通过依赖注入的 transport/DNS fixture 验证，不增加可在正常运行中开启的 ALLOW_PRIVATE_NETWORK 旁路。公开检索的网络权限不能授权真实发信或调用任意外部写接口。

## 6 研究与 CRM 的转换

prospecting_runs 保存研究及有界候选快照；用户确认后原子创建/关联 buyer、contact 和 lead。没有真实联系人时允许只有公司线索，不能自动补人名和邮箱。contact_permissions 维持 unknown，直到出现相应明确证据或只限 simulation 的内部演示授权。

同一 run/candidate 的并发导入只返回一条 lead。研究生成商机或沟通时保留来源；模拟询盘不能写成真实公司曾经提出采购。

本次只执行 A2。目标是让 owner 与 sales 在真实持久化的工作台中处理模拟买家消息，建立第一条外发就必须经过的统一网关基础。

## 建设任务

1. 按 UI_SPEC 和已认可图片实现四入口、会话列表、聊天、按需详情和独立内部区域。买家消息与团队笔记分别读取 messages、team_notes；业务列表不使用硬编码数组或 localStorage。
2. 实现 MockAdapter 的入站事件契约和开发用模拟入口，使用专用模拟账号、确定的事件 ID 与明确的模拟标识。开发入口需要登录与权限，不能成为匿名注入业务消息的通道。
3. 接收模拟事件时确定账号归属、持久化 inbound_events，并通过账号锁建立入站屏障；worker 标准化后创建联系人/会话/消息、更新上下文版本并清除已解决屏障。无法匹配身份的情况进入待确认。

6. 从第一条普通模拟回复起使用 Delivery 命令服务：创建 outbound_request 和冻结 payload、判定授权、同事务 outbox 与入队、worker 原子 claim、MockAdapter 执行、持久化结果。不能先从前端或 Inbox 直接调用 send。
7. 这个阶段免审回复限定为批准过的中性澄清模板，例如请求数量、用途或目的地。未知自由文本先保存为内部草稿，待 C 的 owner 审批路径完成后再外发。价格、折扣或交期没有临时旁路。
8. 完成人工接管的服务端命令。服务端确认前不显示自动处理已暂停；释放接管由有权成员明确操作。human 模式阻止自动 FAQ、自动跟进和旧计划，仍允许当前成员创建符合最新版本的普通受控回复；不能导致人工接管后人工无法回复。

## 必须验证

- 同一个入站事件重放多次只生成一条业务消息；同名不同渠道身份保持可区分。

- 内部笔记不会创建买家出站消息，也不会出现在外发 payload 中。
- 普通模板回复经过网关、入队和 worker；重复点击不生成第二次业务发送。
- simulation 结果显示“模拟执行完成”，数据库不能进入真实 submitted/delivered/read。
- 入站尚未标准化时自动发送被挡住；接管与上下文变更使旧动作失效。
- SSE 断开后重连能从数据库恢复；未授权成员不能借 SSE 订阅或详情接口读到其他工厂内容。
- 一个 thread 关联多个工厂时，读取整段历史必须对全部关联工厂都有权限；不能因为有一条可见商机就泄露其他工厂消息。列表、搜索摘要、SSE、笔记与附件共用这一授权判定。新增关联或成员工厂授权变化后重新验证订阅和后续读取，不实现不可靠的逐消息拼接脱敏。

# 10 阶段 B 供给与报价

只执行 B。目标是让团队从已确认的工厂资料和买家需求生成可追溯、可复核、可保存历史的报价；本阶段生成预览，不绕过下一阶段的商业审批。

## 建设任务

1. 在“产品”入口实现工厂、产品、来源文件/版本、事实/版本、事实确认和价阶的必要操作。只做销售工作需要的界面，不为每张表生成后台菜单。
2. 本地附件通过私有存储服务上传和授权下载，限制类型和大小，记录内容摘要、不可变对象标识及可见范围。授权依赖服务端，不依赖难猜 URL。
3. 明确资料的待确认、已确认、失效或撤回状态；事实能定位到来源版本和片段。成本与对外售价、内部资料与可披露事实分开。
4. 将买家采购需求建为 opportunity；支持数量、规格、目的地、用途、所需日期、语言与待确认项。正式报价前选择工厂，并验证买家、商机、会话与工厂关联。
5. 建立 QuoteCalculator：十进制计算、价阶适用、起订量、设置费、受控折扣、舍入与币种。缺少适用价阶或依据时停止生成完整报价，保留待确认任务。
6. 实现 quotes、quote_versions、quote_lines 和证据引用。一次事务创建版本和所有明细、校验完整性，再冻结；修改通过新版本表达。
7. 生成英文报价预览与 PDF。PDF 内容由同一冻结报价数据生成，包含编号、版本、卖方、收件人、规格数量、单价、各费用、币种、总额、有效期、生产条件及排除项。文件字节生成完成后记录 hash；不能审批后再次重新渲染替换附件。
8. 在对话内部区域展示报价和证据，允许 owner/sales 检查和生成新版本。外发按钮保持待审批状态，阶段 C 才开放真正的审批执行。

## 必须验证的案例

- CT-01：500 × USD 2.40 + USD 30 = USD 1,230；800 件为 USD 1,950。
- 数量越过 500—999 范围、资料过期、跨工厂价阶、未确认事实均不能静默生成有效正式报价。
- 未知运费、税费、样品费显示“不包含/待另行确认”，不能记作已确定的零费用。
- 20 个工作日是附条件的生产周期；六周到货请求保持待确认，不推导为承诺。
- 改数量后生成新 requirements_revision 与报价版本，历史不改写；事实撤回或价格更新使旧版本不可直接发送。
- frozen quote 的父记录与明细不能增删改；预览、API 和 PDF 的金额及条款一致。
- 其他工作区、未授权工厂成员及未登录用户不能下载报价附件或证据。

## 演示数据与时间

种子工厂及供给数据明确写为模拟，不伪造真实供应商确认。初次 seed 根据本次业务演示基准时间生成仍有效的资料和七天报价有效期；测试固定基准时间以便重放。不要把 2026 年某个固定日期写死成永远有效，也不要为演示成功忽略过期检查。

# 11 阶段 C 审批与发送

只执行 C。目标是让“批准哪份内容，就只能执行哪份内容”成为服务端与数据库行为，并在模拟渠道中验证完整失败、重复、撤销和未知结果路径。

## 建设任务

1. 完善 A2 已有发送网关，统一普通回复、FAQ、报价、批次与跟进请求的命令入口；暂未完成的 D/E 生产者只预留类型化调用契约，不创建假业务功能。
2. 定义并测试 canonical payload：最终发件账号、全部收件人、正文、模板参数、报价版本、附件内容 hash 和所需上下文版本。JSON 键排序、十进制表示、空值、Unicode 和数组顺序的规则明确且版本化；收件人顺序的语义需固定。
3. 在同一事务内建立全部快照及证据引用，校验后冻结；审批只引用对应不可变版本与摘要。任何翻译或润色在审批前完成。
4. 实现 owner 的批准、拒绝、撤销及审批历史；校验当前成员有效、角色正确、等于 workspaces.approver_member_id。sales 不能通过请求体伪造 approval、owner 或 authorization_mode。
5. 审批通过、业务状态变更、outbox 和 pg-boss 入队原子提交。相同幂等键同内容返回原结果；同键不同内容返回冲突。
6. 实现发送领取事务：按统一锁顺序检查渠道账号、原始入站屏障、资格/抑制、工厂授权、会话/商机版本、资料、价格、报价有效期、冻结摘要、审批和已有执行。原子更新 claimed、dispatch_token 和 cutoff 时间。
7. 网络调用在事务外进行。定义执行 token/fencing 和恢复协议；每次调用前检查执行权，失效 worker 不发起新调用，结果写回也必须校验 token。不能声称这消除了检查与外部调用之间的全部窗口。没有 provider 幂等能力时，过期 claimed 或任务 lease 到期不得自动重领并重发，应进入 unknown/待核对；支持幂等时也必须复用同一 provider key 并遵守其时效。
8. 完善 MockAdapter：正常执行、拒绝、延迟、重复/乱序回调、接受后响应丢失、支持/不支持 provider 幂等的场景。模拟结果始终使用 simulated 等允许状态，不能伪造真实 delivered。使用独立 simulation schema 的持久接收账本和独立连接，模拟“渠道已接受”的提交与 app 业务投影提交相互独立；账本跨 worker/重启保留，不能用进程内 Map 冒充。该模拟设施不计入 app 的 43 张业务表，API 普通业务角色不能修改它。
9. 实现 unknown 核对界面与服务：复用同一业务发送身份和 provider key，记录核对依据。不能提供不加说明的“再发一遍”快捷按钮。
10. 完善接管、撤销、退订、事实撤销、需求变更与 claim 的串行化协议。claimed 前可阻止发送；之后记录 cancel_requested 并阻止未来尝试，不能显示本次已成功撤回。按请求来源与当前业务授权区分新人工动作和旧自动动作：human 模式允许成员现在发起的受控回复、审批报价及明确批准的当前批次；自动 FAQ/自动跟进和接管前旧计划停止。不要仅凭 created_by_member_id 非空就将自动任务当成人工动作。

## 必须通过的关键测试

- sales 提交、owner 审批；伪造 owner 或免审模式被服务端拒绝。
- 收件人、正文、数量、附件字节、报价版本任一改变，旧审批不适用。
- 业务更新、审批、outbox、入队任一点失败后全部回滚。
- 两个 worker 同时处理同一个请求，只得到一个有效发送 claim；handler 重试不生成第二个业务发送身份。
- 在 claimed 提交前/后注入撤销和接管，得到与 cutoff 一致的结果；不要用不可靠 sleep 模拟并发顺序，使用测试 barrier 控制事务竞争。
- 原始入站已落库、未标准化时，旧自动任务被屏障拦住；收据处理失败也保持阻挡直到明确解决。
- 接受后响应丢失进入 unknown；不支持 provider 幂等时无盲目重发。
- 受控终止 worker 于 claim 已提交但调用尚未开始、Mock 已接受但业务写回尚未完成两个位置；重启后无幂等场景不自动重领，支持幂等场景复用原身份核对。Mock 账本记录接收次数，验证恢复未重复产生副作用；不支持幂等的场景不能由账本暗中去重来掩盖网关错误。
- 重复或乱序回执不会重复创建消息、重复批准或倒退已知状态。
- 旧事实、旧价阶、过期报价、禁用成员或工厂授权失效都会阻挡尚未 claimed 的动作。
- 内部成本、团队笔记、其他工厂资料不进入可发送快照。

## 人工验收路径

sales 提交一份 500 件报价，owner 在最终英文正文和 PDF 预览中确认，执行后看到模拟完成。再改正文或数量，观察重新审批。运行“接受后响应丢失”场景，进入待办核对。演示 claimed 前后撤销的不同界面结果。

## 交付与停点

提交状态转换说明、锁顺序/恢复 ADR 和实际数据库并发测试证据。不能用覆盖率数字代替这些行为。完成后停止，等待用户验收，不进入 D1。

# 13 阶段 D2 批次与跟进

本次只执行 D2。目标是让真实研究线索进入逐人审核与模拟触达，并让报价后的跟进具备负责人、时间、目标和可靠停止条件。

## 建设任务

1. 从已确认候选建立/关联 buyer、contact、contact_point 和 lead。联系方式证据、身份核实与联系资格分别记录；只有公司信息时不能猜测采购负责人或邮箱。
2. 为内部演示建立明确的 simulation 联系资格。它不能改变 email/WhatsApp 的未知或禁止状态。必要时创建独立模拟联系人/渠道身份，标注来源为内部演示，不覆盖真实联系方式。
3. 实现 outreach_batches、不可变版本和逐人 items。每项指向明确的 outbound_request 与最终冻结内容；批次预览包含名单、内容、账号、节奏、时区、截止时间、数量及停止条件。
4. 使用确定性模板生成每个人的初次联系草稿，只填入已核实且可披露的信息，不假装对方已有采购意向。未知内容留空或待人工完善。所有模板与改写在审批前完成。
5. owner 审批实际完整批次，批准后新增名单、修改正文、切换账号或商业条件产生新版本并重新审批；不能把模板批准扩展成无限名单授权。
6. 每个请求通过现有发送网关执行，账号限流与批次节奏由业务状态及 pg-boss 调度；批次允许部分成功、失败或取消，列表逐项展示。
7. 创建 followup：负责人、UTC 到期时间、IANA 显示时区、目标、引用报价版本、内部草稿、执行模式、停止条件与业务版本。默认提醒和草稿；自动模拟跟进必须事先批准最终内容。
8. 改期或改内容递增版本；新回复、接管、退订、商机关闭、需求/报价变化、事实失效时停止旧动作。即使 cancel 队列失败或旧任务仍醒来，也被版本检查拒绝。
9. 统一进入“待办”：待审批、待确认、跟进到期、原始入站失败和发送未知/失败。待办可从领域查询聚合，不为首版新建通用工作流平台。

## 必须验证

- owner 批准的一批 3 个模拟请求可分别成功、失败、延迟，入队不显示全部完成。
- 批次冻结后加人、换内容或换附件失败，必须创建新版本；新版本不继承旧批准。
- 自动跟进再次进入统一网关，不依赖创建任务当时的权限或状态缓存。
- 停止 worker 后到期，再重启：任务仍在，执行前读取最新业务状态。
- 新回复/退订/接管/报价变化/改期分别使旧任务停止；并发多 worker 不重复执行。
- 时区换算及一个存在夏令时变化的 IANA 时区有测试；界面同时清楚显示本地计划时间。
- simulation 联系资格不会授予真实渠道资格，任何 live transport 请求都被本轮配置拒绝。

## 人工验收路径

选取少量真实研究候选，在模拟模式中查看逐人首触达内容并让 owner 审核。执行混合结果场景，检查逐项状态。为报价创建短时间后的跟进，注入模拟买家回复，再观察旧任务因新回复而停止。刷新和重启保留计划与停止原因。

## 交付与停点

交付批次版本、联系资格、跟进状态及停止原因的说明与实际验证。明确这些是真实业务流程中的模拟沟通，不是实际联系了搜索得到的公司。完成后停止，不进入 E。

# 14 阶段 E 模拟 AI

本次只执行 E。本轮用户明确要求先模拟 AI，所以交付可重复、可追踪的业务协作流程。真实模型适配仅保留清楚的接口与后续接入说明。

## 建设任务

1. 定义 AIProvider、输入上下文与 Zod 输出契约，功能包含需求提取建议、资料检索请求、普通问答建议、报价输入建议和跟进建议。
2. 实现 MockAIProvider，使用版本化场景与固定业务时钟。支持范围明确，输入在支持范围外返回 needs_human；不随机生成看似合理的事实、报价或公司资料。
3. 数据上下文由领域服务按 workspace、工厂和披露范围提供。Provider 不能获得数据库万能写能力、审批能力或发送适配器。
4. 模拟 AI 先产生建议，领域服务负责结构校验、事实有效性、计算、权限和当前版本校验。批准、外发、事实确认和真实研究数据变更由正常业务命令完成。
5. ai_runs 使用 execution_mode=preset，provider/mock model_id、scenario_id/版本、输入引用、上下文游标、证据、输出、校验结果、耗时和转人工原因如实记录。没有模型 token 或费用时保持未适用，不编造数值。
6. 内部区域显示“模拟 AI”标签、场景说明、建议与证据。用户可采用/修改/拒绝建议；编辑不能悄悄改写已冻结的外发内容。
7. 支持受控常规 FAQ 自动模拟回复：只有有效且可披露事实、审核过的模板、会话未接管、上下文未过期等条件满足时，才创建 verified_faq_policy 请求并经过网关。
8. 报价、折扣、生产/交期和样品费用始终转业务审批。销售建议可以帮助填写，不具有批准权。
9. 真实获客继续使用确定性来源处理和匹配，不把模拟 AI 当成网页语义理解服务。对外部网页/消息中的指令不执行工具调用。

同一规范化输入、场景版本与业务时钟重放两次得到一致的业务输出；运行 ID 和真实耗时可以不同。记录一次成功、失败、取消和转人工。验证 mock provider 不能直接批准或发送，引用事实撤回后旧建议无法外发。断开真实互联网时，本阶段模拟 AI 功能仍可运行。

## 人工验收路径

对同一材质问题重放两次，查看一致答复与来源；切换为交期承诺，观察审批；移除资料使其转人工；生成建议时注入新买家消息，确认旧建议失效。界面持续显示模拟 AI。

## 交付与停点

交付场景目录、输入输出契约、支持边界、评估结果及未来真实 provider 的接入位置。不能以 mock 结果评价真实模型准确率。完成后停止，等待验收，不进入 V。

# 16 人工验收与失败恢复场景

阶段列表为 **0 / A1 / A2 / B / C / D1 / D2 / E / V，共 9 个节点**。每阶段提示词负责实施范围；本文件补充用户可操作的验收路径和跨阶段负向验证。

## 共同验收前提

- AI 使用可重复的模拟提供方；外部消息只走 simulation；找客户使用真实的 SearchProvider 或 PublicDirectoryProvider。
- SearchProvider 未配置时，只要真实 PublicDirectoryProvider 可用，真实找客户仍可验收；无须为验收强制开通付费账号。两个真实提供方都不可用时，将联网验收记为受阻，不能使用 fixture 顶替成功。
- 下面每项都记录操作、实际结果与必要证据。截图只证明界面显示，数据库、任务和状态行为仍以实际操作与日志为准。
- 数据保存通过刷新、退出登录、停止并重启进程验证。禁止用 reset、重新 seed 或删除 Docker volume 代替持久化验证。

## 0 健康探针与工程启动

1. 按文档在 Mac 上启动 Docker 依赖及 web、API、worker；打开本地健康页，看到各组件的真实可用状态和版本。此阶段只验证运行环境，不应出现假业务数据、假账号或已完成销售流程。
2. 通过健康探针实际检查 PostgreSQL 连接与 worker 活性；不能只有一个固定返回 200 的接口。若使用队列探针，其任务类型明确属于基础设施，不创建客户、消息、报价等业务记录。
3. 停止 worker，健康页应区分 API 可用与 worker 未就绪；恢复 worker 后状态恢复。停止数据库时也应显示具体受影响组件。
4. 关闭并重新启动应用进程，不删除 volume；启动命令可以重复执行，端口冲突和缺失环境配置有明确提示，不需要重新生成工程。

## A1 身份与数据边界

1. 分别以 owner 和 sales 测试账号登录，确认服务端会话真实生效；退出登录后再访问受保护接口，应拒绝访问。
2. owner 可查看授权范围内的工厂；只获工厂 A 权限的 sales 不能通过替换 URL 或接口参数查看工厂 B 的资料。拒绝必须来自服务端，而非仅隐藏导航。
3. 用第二个工作区的测试账号验证跨工作区读取、引用和写入被阻止；错误提示不泄露另一工作区的正文和附件。
4. 查看数据库运行角色证明：API 与 worker 的业务连接不使用 superuser、表 owner 或 BYPASSRLS；认证表、队列表和业务表分别由正确迁移管理。
5. 修改一项可编辑资料或成员显示信息，刷新、退出重登、重启 API 后仍保存；验证过程中不重置数据库。

## A2 消息工作台

1. 从模拟入站入口注入一条带明确事件 ID 的买家消息，经过实际入站持久化与 worker 处理后出现在会话中；再次提交同一事件，不新增第二条消息。
2. 两个成员打开同一会话；一人阅读不应清除另一人的未读状态。刷新和重新登录后，各自已读位置仍保留。
3. 写一条内部团队笔记，确认它只出现在内部区域，不写入外部聊天历史或出站正文。打开买家侧模拟视图时看不到内部笔记。
4. 使用本阶段支持的普通受控回复，检查从 UI 到 outbound request、冻结内容、基础网关、worker、MockAdapter 的真实路径；第一条出站也不能直接由前端调用适配器。尚未具备审批条件的商业承诺应阻止执行或进入待审批状态。
5. 接管会话并断开/恢复前端实时连接；接管以服务端确认状态为准，消息通过游标补查恢复。最终模拟执行显示“模拟完成”，不显示真实已送达。

## B 供给证据与报价

1. 查看 CT-01 的产品、工厂、来源版本、已确认事实、价阶和有效期；点击报价依据能找到实际对应的版本，演示数据具有模拟标识。
2. 对 500 件需求生成报价，检查 500 × USD 2.40 + USD 30 = USD 1,230；改为 800 件后生成新版本，总计 USD 1,950，原版本保留。
3. 检查运费、税费、样品费用等未提供项目明确列为不包含或待确认，不被当作零；超出已确认价阶时要求工厂确认，不能自行外推价格。
4. 检查“20 个工作日”的起算条件和排除项，确认报价没有自动变成“六周内到货”；报价预览与最终附件内容一致。
5. 改变需求或撤销关键事实后，受影响报价显示待重核；刷新与重启后报价版本、计算输入和证据引用仍存在。

## C 审批与完整发送协议

1. sales 提交完整报价的最终正文、收件人和附件；sales 自行批准时被服务端拒绝，owner 可以查看对应快照再批准。
2. 批准 v1 后修改数量、正文、收件人或附件任意一项，产生新版本并要求重审；不能修改已经冻结的版本或沿用 v1 批准发送 v2。
3. 在尚未 claimed 时撤销，待发请求应停止；在发送权已领取后撤销，界面说明正在取消或核对，不承诺已成功撤回。可用受控暂停点稳定复现两个时序。
4. 模拟渠道接受请求但响应丢失，系统进入 unknown 或按适配器明示幂等能力核对；用户不能在状态不明时触发无保护重发。
5. 查看一次完整执行的审计：批准人、目标摘要、报价版本、附件摘要、领取时间、任务和适配器尝试能够对应。最终显示模拟完成，不能被 SQL 或 UI 标为真实 delivered。

## D1 真实找客户

1. 使用真实 SearchProvider 或 PublicDirectoryProvider 搜索/筛选海外公司；实际访问来源并产生结果，结果页明确当前提供方。SearchProvider 无凭据时，不应要求购买才能使用已可用的公开目录提供方。
2. 选择至少两个不同条件或不同公开目录，检查若干不同公司；每条候选能打开来源 URL，展示实际获取时间、摘录/字段、匹配理由和来源类型。空结果可通过空状态测试，但不能替代至少一条真实发现并导入线索的正向验收；不能用演示公司填满列表。
3. 对比公司官网与第三方目录的证据等级。只有摘要或目录信息时显示待复核；未找到的邮箱、联系人、规模、收入等字段保持未知，不生成看似合理的值。
4. 重复运行相同查询，检查域名归并、重复候选和观察历史；新的来源获取不会无声覆盖旧证据。排除一个候选后能查看排除理由。
5. 触发来源超时、页面拒绝或无可用提供方，界面显示具体状态；抓取失败不能标为已验证。额外检查一个私网/回环 URL 被拒绝，且不会访问本地服务。

## D2 触达批次与跟进

1. 从真实研究得到的公司中选择少量候选，核对联系方式来源和资格状态，再生成逐人最终内容；研究结果存在并不自动赋予真实渠道联系资格。
2. owner 在批次预览中逐项查看真实名单、正文、模拟发送账号、节奏和停止条件。冻结后新增收件人或修改内容必须生成新版本并重审。
3. 执行混合成功、失败、延迟的模拟批次，逐项显示实际状态；批次入队不等于全部完成，界面仍持续提示消息渠道为模拟。
4. 为一份报价设置负责人、显示时区、到期时间、目标和跟进草稿；刷新、停止 worker、重新启动后，到期任务仍能恢复，并重新检查当前业务状态。
5. 在任务到期前注入买家新回复、退订、接管或报价变更，旧任务应显示明确停止原因；即使旧队列任务被再次执行，也不能重新外发。

## E 可重复的模拟 AI

1. 使用相同输入、场景版本和测试时钟重放两次，输出一致；界面及 ai_runs 如实记录模拟 provider/model，不显示虚构的实时大模型响应或 token 费用。
2. 输入有确认资料支撑的材质/尺寸问题，观察内部建议与事实来源，再经受控 FAQ 流程模拟回复；最终出站仍通过统一网关。
3. 输入报价、折扣和交期要求，观察建议转入相应业务命令与 owner 审批；模拟 AI 不能直接修改确认价格、批准自身输出或调用适配器发送。
4. 输入缺少资料、证据冲突、过期事实或超出模拟场景的问题，应产生待确认/需人工处理状态，不随机编出答案。
5. AI 生成草稿后再注入新买家消息或人工接管，旧草稿不能自动发送；外部内容要求“忽略审批”也不能改变权限。

## V 本地完整验收

1. 使用真实研究来源找到候选公司，完成资料复核；再通过模拟会话走完询盘、确认需求、报价、owner 审批、模拟执行与跟进计划，整个链路能追溯到业务对象和版本。
2. 重启 web/API/worker 和数据库容器但保留 volume，核对会话、已读、批准快照、研究证据与后续任务仍在；不重新 seed 来掩盖数据丢失。
3. 在独立临时验收数据库验证从空库迁移和初始化，再与已存在本地数据库升级路径分别报告；不能销毁用户正在使用的数据来通过“空库启动”。
4. 按下方跨阶段失败/恢复场景完成必要验证，报告明确区分已验证、阻塞和未覆盖范围。
5. 最终演示持续标明 AI 模拟、消息模拟、客户研究真实；留下可操作的下一会话续接文档，并在等待用户验收时停止。真实 AI 和正式渠道不记为已完成。

## 最终 12 条跨阶段失败与恢复场景

1. **事务回滚与队列一致性**：在批准事务提交前故意报错；批准结果、outbox 事件及 pg-boss 入队全部回滚。重试相同命令不创建重复业务动作。
2. **租户与连接池隔离**：同一连接池交错执行工作区 A/B 请求及 worker 任务；SET LOCAL 上下文不跨事务泄漏，未设上下文不获得业务数据；同工作区工厂授权仍由服务验证。
3. **旧快照与证据失效**：批准后修改需求、换附件或撤销事实；旧批准与旧任务不能放行新内容或失效报价，已经执行的历史快照仍完整保留。
4. **原始入站屏障**：webhook 收据已经提交，但标准化 worker 暂停或处理失败；相关自动出站保持阻挡。处理失败的收据不能静默解除屏障。
5. **领取与撤销竞态**：并发执行 revoke/takeover/opt-out 和 dispatch claim，按照一致锁/版本协议得到唯一可解释结果；claimed 前阻止，claimed 后不虚假承诺撤回。
6. **双 worker 与失去执行权**：两个 worker 同时处理同一请求；正常只领取一次。旧执行者恢复时不能无条件再次调用适配器；使用同一稳定业务幂等键。
7. **外部接受后丢响应**：分别在 claim 提交后调用前、模拟适配器已接受而业务未写回时终止 worker。用独立持久 Mock 接收账本验证；无 provider 幂等能力时过期 claim 不自动重领，恢复进入核对或 unknown，不能靠账本偷偷去重掩盖重复调用。
8. **重复入站与乱序回执**：同一 webhook 多次提交不重复消息或 AI 任务；迟到的低级状态不覆盖更晚状态。模拟事件不能把业务记录提升为真实 delivered/read。
9. **跟进停止与恢复**：停止 worker，期间买家回复或修改报价；重启后旧延迟任务必须读取新状态并取消，不按旧内存草稿发送。
10. **真实检索故障与恶意来源**：搜索限额、目录超时、跳转到私网或含有指令的网页被正确处理；记录真实失败或拒绝，保留旧来源，不制造新客户或执行网页指令。运行中重启仍保留累计请求计数与原 deadline；排除决定不改写证据，旧审核版本不能导入已排除候选。
11. **附件与内部资料边界**：冻结附件后尝试覆盖对象、替换下载内容或使用其他工厂/内部成本资料；摘要与权限检查阻止出站。内部团队笔记不进入外部 payload。
12. **持久化与备份恢复**：在独立恢复环境恢复数据库与附件对象，核对报价、批准、出站快照和附件摘要；恢复后未完成任务重新过网关，历史模拟任务不能切换到正式账号执行。

## 验收记录要求

- A2 的普通回复也必须具有基础网关、真实持久化和模拟执行路径；C 扩展审批规则，不能首次才引入发送边界。
- 本轮真实找客户不依赖真实 AI；规则提取和匹配须可解释，模拟 AI 不能补造公司资料。
- 用户阶段验收只影响开发进度，不构成对某个业务报价或触达批次的 owner 批准。
- 每阶段可以进入 ready_for_user_review；只有用户确认或明确发出后续阶段指令后，才记为 accepted。
